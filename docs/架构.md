# 技术架构

这份文档回答三件事：**用什么语言写**、**依赖怎么管**、**动画底子选谁**、**测试怎么算做扎实**。
结论先行，理由在后。

---

## 1. 语言：TypeScript，不引入 Python

**结论**：算法层继续用 TypeScript，**不引入 Python**。

理由：

1. **算法性质是确定性的数值计算**——路径解析、弧长重采样、光栅化、模板匹配、轮廓插值、
   版面生成。没有一个环节需要 Python 的生态（NumPy/SciPy/PyTorch）。
2. **同一份代码要能在浏览器里直接跑**。演示页的核心诉求是「零构建、任何静态服务器都能跑」，
   算法必须在页面里执行。TS 一份源码同时是库、是 npm 包、是演示页依赖；换成 Python 就得
   再养一份实现或一条服务端链路。
3. **现在最缺的不是第二种语言，是把异常钉死**。见 §4。
4. **将来真要用 Python 时的正确接法**：把本库当**库**用——`npm` 发包后由 Python 侧调子进程
   或 HTTP；或者只移植 `src/geometry`（纯几何、无 IO、无依赖）这一层。
   **不要**把仓库一分为二维护两套实现。

选型时也评估过 Pyodide（浏览器里跑 Python）：体积大（~10 MB wasm）、
类型检查断链（Python 侧没有 TS 的类型保障）、调试链路长。为「跑同一份算法」付这个代价不划算。

---

## 2. 分层：算法层纯函数，IO 全部外置

```
hanzi-glyphs-svg     数据层   字形文件 + 出处（provenance）
hanzi-relations      数据层   字↔释义/异体/笔顺（待建）
hanzi-algorithms     算法层   本仓库：纯函数，运行时零依赖
```

**硬约束**：`src/**` 里的每个导出都是**纯函数**——
输入是 `Glyph` / 选项对象，输出是结构化结果 + 置信度；
**不读文件、不发网络请求、不碰 DOM、不写盘**。
所有 IO（读 SVG、落 JSONL、起服务器）都在 `tools/` 与 `demos/`。

这条约束带来三样东西：

- 算法能**离线跑**、能**确定性复现**（同一输入必得同一输出），测试才有意义；
- 下游（游戏、编辑器、教学 App）能直接 `import` 算法去做实时计算，不必拖一整套 IO；
- 算法与素材**解耦**：字形换了、素材来源变了，算法不用改。

## 3. 依赖策略：核心零依赖，演示层允许 vendor

| 层 | 依赖 | 规则 |
|---|---|---|
| `src/**` | **零运行时依赖** | 下游 `import` 我们的算法不该被拖上一个动画引擎 |
| `demos/**` | 允许第三方 | 版本钉死 + 许可全文随附 + 产物入库 + 可复跑重建 |
| `tools/**` | devDependencies | 只在开发期用 |

**为什么演示页允许 vendor，而核心不允许**：演示页是**核验工具**，跑在作者本机，
要能离线跑、要能锁版本；而算法库是要给下游用的，多一个运行时依赖就是多一份负担。
两者是不同性质的东西，用不同规则管。

**vendor 的四条硬约束**（缺一条就违约或不达标）：

1. **版本钉死**——写死具体版本号，不写 `^`、不写 `latest`；
2. **许可全文随附**——放在产物旁边的 `*.LICENSE.md` 里，不是在 README 里写一行「MIT」；
   MIT 第 1 款要求许可声明随附在软件的所有副本里；
3. **产物入库**——`demos/lib/vendor/*.js` 进版本库，保证「零构建、离线可跑」；
4. **可复跑重建**——`tools/build_vendor.ts` 能从 `node_modules` 重新产出同样的文件。

## 4. 动画底子：两个库，各管一段

### 4.1 选型过程

先看了 2026 年当下最热的几家：

| 库 | 许可 | 体积（min/gzip） | 结论 |
|---|---|---|---|
| **GSAP 3.13+** | GreenSock 标准许可（非 OSI） | ~60/25 KB | 3.13 起全插件免费（含 MorphSVG、DrawSVG），但**许可不是 MIT**——对一个 MIT 仓库来说混进非 OSI 条款不合适，体积也最大。**弃** |
| **anime.js v4.5** | **MIT** | ~46/17 KB（裁剪后） | 2025 年重写，ESM + 类型齐全，内置 SVG path 绘制与 morph。**采用** |
| **Motion 14**（原 Motion One / Framer Motion） | MIT | ~18/6 KB | 基于 WAAPI，做不了「每帧驱动算法重算路径」；我们需要的描边绘制能力 anime.js 直接就有。**备选** |
| **原生 CSS / WAAPI** | — | 0 | 够做简单过渡，但做不了时间线编排与逐帧回调。**不够** |

再叠一层领域判断：**汉字笔顺动画已经有成熟的现成底子**——
[hanzi-writer](https://github.com/chanind/hanzi-writer)（MIT，4.1k★，2025-09 仍在发版），
它是这个领域事实上的标准做法：真笔顺数据 + 逐笔书写动画 + 描红练习。
自己用 `stroke-dashoffset` 重写一遍，既费劲又不如它对。

### 4.2 最终分工

```
hanzi-writer   领域专用   汉字笔顺：真笔顺数据、逐笔书写、描红练习
anime.js v4    通用引擎   时间线、缓动、逐帧回调、SVG 描边绘制
```

- **hanzi-writer** 负责「一笔从头到尾」——它知道汉字，知道笔画顺序，知道怎么把一笔画出来；
- **anime.js** 负责「字形怎么演变」——时间线编排、缓动曲线、每帧回调驱动算法重算中间形。

让 hanzi-writer 去驱动字形演变是不合适的（它不懂「两个书体的同一字」）；
让 anime.js 去处理笔顺也是多余的（hanzi-writer 已经做好了，而且数据更准）。

### 4.3 数据许可要分清

| 东西 | 许可 | 处置 |
|---|---|---|
| hanzi-writer（代码） | MIT | vendor 进 `demos/lib/vendor/`，许可全文随附 |
| anime.js（代码） | MIT | vendor 进 `demos/lib/vendor/`，许可全文随附 |
| hanzi-writer-data（笔顺数据） | **Arphic Public License** | 只在本地 `assets/` 使用，**不入库、不发布**；许可与出处记在 `THIRD_PARTY_NOTICES.md` |

本仓自己的字形层不发布字形，笔顺数据同理——**数据留在本地，代码才进库**。

### 4.4 anime.js 的裁剪

anime.js 的发布包是「全家桶」UMD（118 KB min），含 draggable / scroll / layout / text
等跟本仓库无关的模块。`tools/vendor/anime-entry.ts` 只导出用得上的部分，
`tools/build_vendor.ts` 用 esbuild 摇成 **46 KB** 的 IIFE（全局 `Anime`）。

## 5. 测试策略：把「异常情况」钉成可断言的行为

用户反馈「现在异常情况很多」。这句话有两层意思：
① 算法在退化输入上会炸或会给出离谱结果；② 演示页的输出看着不对。
两层都要治，但治法不同。

### 5.1 每个模块五层测试

| 层 | 测什么 | 为什么 |
|---|---|---|
| **① 正常路径** | 典型输入 → 预期结果 | 基本盘 |
| **② 边界** | 空串、单元素、刚好越界、奇偶 | 边界是 bug 高发区 |
| **③ 退化输入** | 空数组、零尺寸、NaN、Infinity、负数、超大数 | **核心**：不许抛异常。要么给合理结果，要么明确返回空/空数组 |
| **④ 不变量 / 性质** | 确定性、互不重叠、往返一致、配对一一对应 | 抓「看起来对其实错」的错 |
| **⑤ 真实字形端到端** | 有 `assets/` 时跑真字形 | 算法要真能用 |

**第 ③ 层是这轮的验收标准**：把每一条「异常情况」写成一条断言，
钉死它应该抛还是应该返回什么。以后改算法时，这些行为不许无声漂移。

**第 ⑤ 层的纪律**：没有本地字形素材时**跳过**，不许红——
测试失败要能说明「算法坏了」，不能只是「素材没同步」。

### 5.2 CI 门禁

```
typecheck:all   →  src + tools + tests 一起过 tsc
build           →  tsc 出 dist/
test            →  vitest
bundle 一致性   →  demos/lib/hanzi-algorithms.js 与 src/ 一致（重跑打包后 diff 必须为空）
vendor 一致性   →  demos/lib/vendor/ 与 tools/build_vendor.ts 产出一致
```

工具与测试同样跑在 Node 上，所以 `tsconfig.json` 只管 `src/`，
工具与测试用 `tsconfig.tools.json` 单独一起查——否则那两处的类型错误会漏网。

## 6. 演示页的三条约定

演示页是**核验工具**，不是产品。但它呈现的就是这个库的对外形象，所以有约定：

1. **三栏对照优先于单栏**。算法输出旁边摆上**真实摹本**（或对照值），
   让人一眼看出算法对不对。单栏的「算法说啥就是啥」没有教学价值——
   隶变算法原来的演示就是这样，看着「很乱」又「没什么用」。
2. **生成的中间形态必须标「算法生成」**。形变插值出来的过渡形不是任何历史书体的摹本。
3. **低置信度时显示「说不准」**，不硬给答案。部首定位置信度不足返回 `null` 是有意为之。

## 7. 目录约定

```
hanzi-algorithms/
  src/                    算法实现（TypeScript，运行时零依赖）
  tests/                  vitest 单测 + 真实字形端到端断言
  tools/                  同步素材、生成索引、生成数据集、评审探针
    vendor/               vendor 库的裁剪入口
  demos/
    lib/
      hanzi-algorithms.js 算法打包产物（入库）
      vendor/             第三方库的裁剪产物 + 许可全文（入库）
  docs/                   设计取舍与踩坑（为什么这么做）+ 本文件（怎么搭）
```

**保持精简，勿随意增加顶层目录。**
