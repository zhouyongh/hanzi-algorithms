# 设计取舍与踩坑

这份文档记录**为什么这么做**，以及实现过程中踩过的坑——它们大多不是从代码里能看出来的。
新加算法前先读一遍，免得把同样的坑再踩一遍。

---

## 一、整体取舍

### 1.1 为什么算法层单独一个仓库

三层架构：

```
字形层  hanzi-glyphs-svg    字形文件 + 出处（数据）
关系层  hanzi-relations     字↔释义/异体/版本（数据，待建）
算法层  hanzi-algorithms    结构计算 + 形变 + 排版 + 教学（代码 + 示例）
```

字形数据与结构计算的生命周期完全不同：字形是「素材」，一年可能只动几次；
算法是「产品」，每周都在改。混在一起会让两边都难维护。

### 1.2 为什么字形不随库发布

字形来自兄弟仓库，**本仓库不复制**（`assets/` 与 `data/` 全部 gitignore）。
理由是许可：甲骨层是 CC BY 4.0（要署名、要标注改动），汉典那几层是 CC0，
但**底本出版物的著作权并未因汉典的 CC0 宣告而消灭**——这层链条由作者另行确认，
算法库没有必要替它承担风险。

派生数据（`data/*.jsonl`、部首定位结果、笔画对应关系）**同样不入库**：
它们是从字形算出来的，性质与字形相同。

代价是演示页不能「clone 下来双击就开」——这是有意的取舍。

### 1.3 为什么 TypeScript 而不是 Python

演示要的是浏览器里的交互，而浏览器 SVG 原生就有
`getPointAtLength`（路径等距采样）、`getTotalLength`、`isPointInFill`（命中测试）、
path 插值——**恰好就是这套算法需要的原语**。用 Python 做同样的事等于把浏览器
免费给的能力再实现一遍。

代价是 NCC 匹配要自己写 FFT。规模不大（基 2 FFT 约 120 行），换来的好处是
**运行时零依赖**：下游 `npm install` 不会拖进任何东西。

## 二、算法上的坑

### 2.1 部首定位：核心洞察与三个必踩的坑

**核心洞察**：部首字形本身就是仓里一张现成的小篆（说文 540 部，每个部首字都有
独立的篆书字形）。于是「识别未知的部首」变成「在复合字里定位一个已知形状」——
标准的模板匹配问题。

**坑一：必须用归一化互相关，不能用最大重叠量。**
小模板落在一块实心墨里，重叠量也是满分。「語」的言部一开始就被匹配到了右上角
的错误位置——因为那里的笔画又密又小。改用 NCC（相关度 ÷ √(窗口能量 × 模板能量)）
之后，密度不再影响「像不像」。

**坑二：FFT 的浮点噪声会决定并列位置的胜负。**
相关度算出来是 1.0 和 1.0，实际是 1.0+1e-10 和 1.0-1e-10——**噪声决定了谁赢**。
必须把相关度量化到 1e-6 再比较。

**坑三：小模板会「冒充」整个部首。**
匹配框只截取了一根粗笔画的一段时，局部是完美匹配。要用**连通域精确率**
（框内墨量 ÷ 框所触及的全部连通域的墨量）做并列裁决：真正的部首作为完整的一组
笔画被框住时，精确率接近 1；截取一段时精确率很低。

**坑四：尺度必须各向异性搜索。**
部首作偏旁时常被纵向拉长——实测「手」作偏旁时横向压到 0.50、纵向保持 0.90。
等比缩放找不到这种解。搜索时横纵独立，且细搜用**直接计算**而不是 FFT：
候选有两百多个，但每个候选只在等比解附近算，比每个都做全图 FFT 便宜一个数量级。

**坑五：部首可能互不相连。**
篆书的「水」作偏旁是三条**分离**的曲线，篆书的「日」是三段不相接的框。
所以**不能用连通性把不相邻的笔画剔掉**——那会把氵 只留一条。判定只按
「墨量落在匹配框里的比例」，连通性只在有多个互不连通的组时用来择一。

### 2.2 描红评分：三重坐标换算

把「学生的字」和「范字」放到同一张画布上比对，要过三关：
**掩膜像素 → 源用户单位 → 目标画布像素**。

中间那一步最容易错：
- 掩膜是按 `viewBox` 光栅化的 → 掩膜像素要除以 `viewBox` 尺寸才能回到用户单位；
- 归一化矩阵（`fitToBox`）的输入输出都是**用户单位**，不是像素；
- 矩阵算出来的结果**已经是目标像素**，不能再乘一次分辨率。

踩过一次：少了 viewBox 这一步，IoU 恒为 0，所有描红评分都错。

### 2.3 部件描述子：不能用「用户单位的包围盒」判空

单独一条横线在用户单位里**高度是 0**，但它确实有墨。用用户单位的包围盒判空
会把这种部件算成「没有部件」，描述子变成全 0，于是所有单横线的部件会聚成一族。

判空要看**光栅化之后**的墨迹。

**坑六：挑不出部首笔画时，要返回空，不要返回「部首为空」。**
早期版本里，部首路径一条都没挑出来时仍返回一个匹配结果（路径集为空）。
下游的构形分解拿到空部首，就把「剩余部分」当成整个字，于是判成「包围结构」。
实测这让 **42% 的字得到错误构形**（⿵ + ⿴ 占 74%，而形声字多是左右/上下）。

现在的做法：
- 部首路径一条都挑不出来 → `locateRadical` 返回 `null`（**不敢下结论**）；
- `decompose` 拿到空部首 → 返回 `null`（**说不出结构就不说**）；
- 路径阈值从 0.6 放宽到 0.4：实测（200 字样本）0.6 会让 18.5% 的字一条笔画都挑不出，
  因为部首作偏旁时被拉长，匹配框常常只盖住它的一部分。

**教训**：算法「不知道」的时候要说不知道。返回一个错的答案，比返回空糟糕得多——
下游不会怀疑它。

### 2.4 声族聚类：贪心会串链

按声符形状聚类时，最初的写法是「新成员只要跟**代表**够像就并进去」。结果最大的一族
有 156 个成员，混进了玉部、艸部、足部、訁部毫不相干的字。

两条修正：

1. **必须和族里每一个成员都够像**，不能只跟代表比；
2. **只收左右/上下布局的字**——包围结构（⿵⿶⿷）的「剩余部分」是字芯，不是声符。

修正后同一批数据里出现的族长这样：玎/玤/玪/瑚、珛/琫/珠、瑛/琰/璅、莠/苽/芼 ——
形态上确实是一家。仍有少量跨部首的误并（这是「按形聚类」的固有代价，
文档里写明了：真正的声族要看韵书，这里只是「长得像一家」）。

### 2.7 部首定位：路径找对了，构形判不对——**准确率 62%，而且原来的 37% 本身就是错的**

部首定位分两步：**找出部首是哪几笔**，和**判出构形**（⿰/⿱/⿵/⿴）。
第二步在 92 个「说文部首 ≠ 整字」的可分解标注字上 **62.0%**。

这一节是整个仓库改动最大的一处。三轮修正：
**37%（报的）→ 23.3%（分母修正后）→ 62.0%（解析器修正后）**。

#### 头一个坑：37% 这个数字是怎么错的

早先报的「37%（46 个标注字）」有两处问题，叠在一起把数字抬高了将近一倍：

1. **分母是错的**。评测脚本遇到「篆书层里查不到这个字」「没有说文部登记」
   「部首字形缺」时直接 `continue`，**不计数也不报告**。70 个标注字里有 24 个
   被这样静默丢掉，剩下 46 个。而且丢掉的**多是 ⿱/⿵/⿴**（草、花、問、國、園……），
   样本被系统性偏向左右与独体。
2. **46 个里有 17 个是平凡正确的**。說文 540 部里，**60 来个部本身就是合体字**
   （林、里、男、宮、明、朙、日、旦、晶、有、冥、齊、鼎……）。
   对这些字，说文部首**就是整字**，「部首 + 剩余部分」这个前提不成立，
   算法只能给 ⿻。把它们算进准确率，等于白送 37 个百分点。

现在评测脚本把三组分开报：

- **可分解字**（说文部首 ≠ 整字）：**92 个，准确率 62.0%** ← 头号指标
- **说文部首就是整字、IDS 也是独体**：56 个，平凡正确，单列
- **说文部首就是整字、但 IDS 是合体**（林、里、男、宮、明）：前提不成立，不计入
- 篆书层里没有的：脚本明确报出几个、为什么，不再静默跳过

**教训**：一个准确率数字要连**分母怎么来的**一起交代，否则没人知道它量的是什么。
「37%」这个数字本身没错，错的是**量的方式**。

#### 头一个真 bug：路径解析器把「洞」丢了

**这是整轮最大的发现。**

小篆的「日」在 SVG 里是**一条路径、三个子路径**：外轮廓 + 两个**反向绕向**的洞
（上格、下格）。中间那道横留在墨里，两个格是空的。浏览器用 nonzero 规则渲染，
出来是一个**带横的框**——实测截图确认过。

而本仓库的解析器 `parsePath` 有个 bug：

```ts
// 早先的代码
if (relative && started) { x += cx; y += cy; }   // started 在 z 之后被置 false
```

`z` 之后**当前点回到本子路径的起点**（SVG 规范如此），紧跟着的相对 `m`
必须相对这个点算。代码却在 `z` 之后把 `started` 置了 false，于是**相对偏移被丢掉**。

「日」的路径是 `m…z m…z m…z`——后两个 `m` 都被当成绝对坐标，
两个「格」被放到完全错误的位置。结果：

- 洞没了 → 「日」渲染成**实心块**，「目」也是；
- 字形整体歪了 → 「日」的墨迹范围从 229×322 变成 522×502；
- **演示页画出来的也是错的**（它用的是同一份解析结果）。

**影响面**：六个书体里 **58%–79%** 的字形都踩了这个模式——

| 书体 | 字形数 | 含「z 后接相对 m」 |
|---|---|---|
| 甲骨 | 11,416 | 59.2% |
| 金文 | 8,290 | 66.5% |
| 篆书 | 10,591 | 58.4% |
| 隶书 | 11,947 | 66.5% |
| 傳抄 | 29,260 | 59.7% |
| 楚简 | 22,371 | 78.9% |

也就是说，**整个库一直在对一半以上被挪错位的几何做计算**。

修法是一行：相对 `m` 永远相对当前点（路径开头当前点是 (0,0)，加不加一样）。
修完之后：

- 「日」「目」「明」都渲染正确了（见 `assets/report/parse-日.svg` 与浏览器对照）；
- **模板法准确率 23.3% → 33.3%**；
- 偏旁形码本也跟着重归纳（原来是用坏几何归纳的），覆盖的部从「只有手这类」
  变成 125 部，**「目」「水」「女」「言」都进去了**。

**教训**：视觉输出不对劲时，**先怀疑数据通路，别急着调算法参数**。
这一轮在算法上调了好几轮参数（子路径划分、质心判据、投票法组合），
真正的病根在解析器——而且它藏在「渲染出来的形状明显不对」这个信号里，
本来第一眼就该看见。

#### 根因二：部件的划分单位错了——`<path>` 不等于部件

篆书层里一条 `<path>` **常常含多个子路径**（实测 35% 的路径不止一个子路径，最多 13 个），
而这些子路径**不一定属于同一部件**：

- 「眼」有 2 条路径。路径 0 是「艮」——但它含 4 段子路径，最上面那段**横帽
  一直伸到字的左边**；路径 1 是「目」（框 + 两横）。
- 早先按**路径**取外接框，「艮」的框因此横跨整个字，构形判不出来。

改成**按子路径**划分（`RadicalMatch.perSubpath`）后，「投」「眼」这类字立刻判对。

#### 根因三：几何判据用外接框，而篆书的部件常交叠

「眼」的「目」和「艮」横向重叠 90%，两个框的重叠比于是 1，左右结构被判成包围。
但**墨量**的分布是稳的：「目」的墨在左，「艮」的墨在右，哪怕它们交叠。
改用**墨量质心**（`geometry/path.ts` 的 `centroidOf`）判断左右/上下。

#### 根因四：⿵/⿶ 两个分支写反了

早先的代码里「部首框套住其余部分」判成 ⿶、「其余框套住部首」判成 ⿵——
**正好反了**。IDS 的 ⿵ 是**左上包围**（問 = ⿵門口），
⿶ 是**右上包围**，不是「其余在部首里面」。

而且 ⿴（全体包围）与 ⿵（左上包围）在几何上**分不开**：两者都是「部首框套住其余部分」，
框的外接框跟整字一样大。区别在**部首本身是不是闭合的框**——
「囗」闭合（國 = ⿴囗或），「門」「匚」「厂」开口（問 = ⿵門口、匪 = ⿵匚非）。
所以用 `raster/mask.ts` 的 `hasEnclosedHole` 看部首独立字形有没有封闭空腔。

#### 根因五：结构符混了两种语义

结构符一度同时表达两件事：IDS 的**版面**（⿰ 左形右声）与**部首在哪一侧**。
于是「部首在下」只能借用 ⿷（IDS 里是「左下包围」），自相矛盾。

现在分干净了：

- **结构符按 IDS 版面语义**：左右 ⿰、上下 ⿱、包围 ⿵/⿶/⿷/⿸/⿴；
- **部首在哪一侧由 `radicalSide` 单独给**（left / right / top / bottom / enclosing / whole）。

「想」= ⿱相心：版面是上下（⿱），说文部首「心」在下（`radicalSide: "bottom"`）。
这一改单独就涨了十来个百分点——之前「部首在下」的一批字全被判成 ⿷。

#### 三条路径的实测对比（92 个可分解字）

| 路径 | 做法 | 正确 | 判错 | 判不出 |
|---|---|---|---|---|
| 模板法 | 拿部首的**独立形态**做模板匹配 | 33.3% | 54.4% | 12.2% |
| 投票法 | 拿归纳出的**偏旁形**按笔画形状投票 | 28.9% | 12.2% | 58.9% |
| **组合**（默认） | **投票优先，判不出回退模板** | **62.0%** | 26.1% | 12.0% |

两条路径是**互补**的，不是替代关系：

- 投票法准（判错只有 12.2%），但只在**归纳出了偏旁形**的部上可用（覆盖 125/540 部），
  没有偏旁形的部它连判都判不出（所以判不出率高达 58.9%）；
- 模板法哪都能用，但说文部首的独立形态跟它在合体字里的偏旁形态常常不同
  （「水」独立是中间一竖两边四点，作偏旁是三条波浪线），于是常落在错处。

**为什么组合比任何单用都好**：它把「准」和「广」拆开，各取所长。
而且这不是凑出来的——「眼」和「語」上两条路径是**互相矛盾**的：

- 「眼」= ⿰目艮，小篆的「艮」里本来就含一个「目」形的框，**形状上分不开**；
  模板法找到的是「艮」（ncc 0.766），偏旁形投票法找到的才是「目」。
- 「語」= ⿰言吾，模板法落到右边的「吾」上，偏旁形投票法找到左边的「言」。

**偏旁形（拿这个部「在合体字里惯用的写法」去比）才是分得开的关键**——
这正是最初设计投票法时的直觉，只是当时几何是坏的，测不出这个差别。

**投票法的形状距离容差**（`typeTolerance`，默认 34）实测：
26 → 58.7%、30 → 59.8%、34 → 62.0%、38 → 63.0%、44 → 60.9%。
取 34（在平台上，不取峰值，免得对这一组标注过拟合）。

#### 光栅化的取景（早先的一条，保留）

上游篆书字形声明 `viewBox="0 0 400 400"`，但路径坐标会跑到框外
（实测「明」的墨迹 x 到 −124、y 到 −171）。按声明框光栅化会裁掉三分之一的字，
匹配于是建立在**残缺形状**上。改成按**墨迹范围**取景后：

| 取景 | 模板法 | 投票法 | 判不出（模板法） |
|------|--------|--------|------------------|
| `ink`（墨迹范围，默认） | 37.0% | **23.9%** | **5** |
| `viewBox`（声明框） | 37.0% | 15.2% | 7 |

（这组数字是解析器修好**之前**测的；`ink` 优于 `viewBox` 的结论不变。）

模板法两者打平，但 `ink` 判不出更少；投票法 `ink` 明显更好。
**根因**：偏旁笔画多在字的**边缘**，而边缘正是声明框裁掉的地方——
`viewBox` 裁掉的恰好是部首笔画。

`frame` 开关因此留在 API 上（`RadicalOptions.frame`），默认 `ink`，
`viewBox` 保留是为了「对比两幅取景的差异」这类用途。

#### 一处刻意的粒度不一致

部首定位的**路径级**选择（`match.pathIndices`）与**子路径级**选择（`perSubpath`）
有时不一致，原因是两边的「参照物」不同：

- 偏旁形码本是**按路径**归纳的（每条路径一个形状描述子）；
- 投票法却**逐子路径**比形状（因为几何判定要更紧的区域）。

实测「語」= ⿰言吾：部首「言」横跨路径 0 与路径 3，路径级选中 [0,3]，
子路径级只挑出路径 3 的子路径。

取舍：**几何判定用子路径级**（实测 62.0% vs 58.7%——部首区域收紧，
质心判据才不会被非部首的笔画带偏）；**报出来的路径清单用路径级**
（与界面高亮的一致，说的是同一件事）。
所以 `Decomposition.radicalPathIndices` 与几何用的区域偶尔对不上，这是有意的。

#### 还没解决的

**形态**仍然是最大的瓶颈：说文部首的**独立形态**跟它在合体字里的**偏旁形态**不一样。
投票法绕开了它（用偏旁形去比），但偏旁形码本只覆盖 125/540 部，
其余 400 多部只能退回模板法。

下一步该走的方向：**字形切分**——先把字切成构件，再拿构件去比；
或者引入 IDS 数据做监督，把「哪些笔画是部首」变成可训练的问题。

#### C1 的两处实现缺陷（看演示页时才发现）

在浏览器里拖滑块看效果时，发现形变的中间态**糊成一坨实心黑块**。两个原因：

1. **描边型与填充型混着插**。甲骨骨架的笔画是**折线**（开放路径），
   摹本轮廓是**闭合轮廓**。`normalizeGlyph` 把折线当闭合轮廓去插值，
   填充后就是实心块。
   修法：先把折线按笔宽左右偏移成**闭合的带状轮廓**（`strokeToContour`），
   两种形态就统一了。
2. **「没配上的笔画」的淡入淡出方向写反了**。
   目标里没配上的笔画应当随 t **长大**（t=0 看不见、t=1 完整），
   写成了 `1 - t`（随 t 收缩）；源里没配上的应当随 t **消失**，
   写成了 `1 + 0.6t`（随 t 放大 1.6 倍）。
   结果是**连 t=1 都不是目标字形**——源里多出来的笔画反而长大了。

修完之后端点对、中间态可读（见 `assets/report/evolution-strip.png`）。
新增 `tests/morph.test.ts` 守住：端点要对、中间态不能糊、归一化后折线要变成带。

中间态仍然不算好——那是**对应关系**的问题（见上一段），不是插值本身。

#### 教训

- 测出准确率不是终点，**知道自己为什么只有这个数**才是；
  而「知道自己为什么只有这个数」的第一步，是**确认分母是怎么来的**——
  这一步晚了很久，代价是曾经对外报过一个虚高一倍的数字。
- **视觉输出不对劲时，先怀疑数据通路**。这一轮在算法上调了好几轮参数，
  真正的病根在解析器，而且它就摆在「渲染出来的形状明显不对」这个信号里。
- 两条算法路径**看起来是替代关系，实际是互补**——先量清楚各自的「准」与「广」，
  再决定怎么合。

### 2.9 C1 跨书体对应：「92.3% 可建立对应」是个弱指标

之前 README 写「甲骨 ∩ 篆 = 852 字，92.3% 可建立部分对应」。这句话本身没错，
但**容易被当成质量指标**——「可建立对应」只是说「至少能找出一对重叠的笔画」，
不代表对得好。

路径解析器修好之后（几何不再被挪错位），实测各段对应的置信度其实很低：

| 字 | 甲骨→金文 | 金文→篆 | 篆→隶 | 隶→傳抄 | 傳抄→楚简 |
|---|---|---|---|---|---|
| 日 | 0.68 | 0.19 | 0.11 | 0.32 | 0.20 |
| 月 | 0.53 | 0.16 | 0.27 | 0.62 | 0.68 |
| 山 | 0.48 | 0.15 | 0.33 | 0.51 | 0.75 |
| 水 | 0.18 | 0.33 | 0.21 | 0.76 | 0.11 |
| 目 | 0.23 | 0.25 | 0.57 | 0.25 | 0.47 |
| 木 | 0.23 | 0.40 | 0.51 | 0.38 | 0.65 |

修几何**之前**这些数字是 0.11–0.95，看着更高——那是因为错位的几何
**偶然**产生了更多重叠。数字变低是**变准了**，不是变差了。

结论：形变插值能跑、中间态是合法路径，但**对应关系目前不可信**——
演示页该按「示意」讲，不要说「这一笔就是那一笔的演变」。
要真做对，得上 IDS/部件级的对应数据做监督，不能只靠笔画重叠。

### 2.8 教学类算法：三处该说清的边界

挨个过审（`tools/review_algorithms.ts`）时把这三处挑了出来，
前两处改了，第三处记下来。

#### E2 描红评分：笔顺写反原来拿满分

逐笔得分是**按形状**算的——「这一笔像不像那一笔」。
所以学生把第 1 笔和第 2 笔的**形状写反了**，每一笔还是都能配上，
总分照样满分。对描红教学这是漏洞：学生不知道自己顺序错了。

改成：额外判一次**笔顺**——学生的每一笔最像范字的哪一笔，
这些编号应当递增；不递增就是笔顺反了，扣两成（`orderPenalty`，默认 0.8），
并给出「第 N 笔写成了第 M 笔的样子」这样的提示。可以在
`EvaluateOptions.penalizeOrder` 关掉。

#### E5 笔顺检查：对甲骨字是纯误报

早先的检查一律报「笔序可能有误」，但**描边型（甲骨骨架）字形的文件顺序
就是落笔顺序**（构造如此），笔画之间不衔接是常态——推不出「笔序有误」。

现在分两种字形说：
- **骨架**：不相接只是事实，报告「骨架字形的笔画各自独立，文件顺序即落笔顺序，
  无笔序错误可查」，不判错。
- **摹本**：路径顺序本就不承载笔顺信息，不连续只能说「这一串不像一条连续的笔顺」。

#### E7 声族聚合：描述子的分辨率把族既串链又拆散

全量数据集（10,591 字）跑完后看声族，发现两个方向相反的问题：

1. **最大族 199 笔，语义部横跨示、玉、牛、足、言、革、寸、攴、目、鸟……**
   ——这是**串链**，不是声族。600 字的小样本看不出来（最大族 10 笔），
   全量才暴露。
2. **真正的声族被拆散**——同一个声符的字落在不同的族里。

根因是描述子的**光栅化分辨率**：

    // 早先的代码
    const part = rasterizeGlyph(subpaths, {
      width: size * 4,        // 64×64
      height: size * 4,
      viewBox: glyph.viewBox, // ← 整字的画布！
    });

部件只占整字的三成，在 64×64 的整字画布上就只剩十几个像素，
再缩到 16×16 满是量化噪声——同一个声符写得大小位置略不同，描述子就差很多。
改成**在部件自己的包围盒里光栅化**：分辨率只跟部件有关，描述子就真的只看形状。

阈值也是量出来的（1500 字样本，	ools/diag_family_sweep.ts）：

| 阈值 | 族数 | 最大族 | 最大族里的语义部种类 |
|---|---|---|---|
| 16 | 1284 | 10 | 1 |
| 20 | 1240 | 12 | 1 |
| **24** | **1175** | **8** | **4** |
| 28 | 1085 | 19 | 5 |
| 32 | 992 | 21 | 8 |
| 36 | 889 | 24 | 6 |
| 40（旧默认） | 789 | 58 | 8 |

默认阈值 40 → 24。

1500 字样本上：最大族从 58 笔降到 8 笔，族里的语义部种类从 8 降到 4。
**全量（10,591 字、7,635 字参与聚类）实测**——串链在规模上是会放大的，
所以样本上的数不能直接用：

| | 声族数 | 最大族 | ≥50 成员的族 | 中位族大小 |
|---|---|---|---|---|
| 阈值 40（旧） | 1,187 | **199 笔** | 10 个 | 3 |
| **阈值 24（新）** | **1,430** | **42 笔** | **0 个** | 2 |

再紧（20）族最干净（语义部 1 种）但会把真族拆散，所以取 24。

**还留着一个坑**：这个算法是**按形聚类**，不是按读音聚类。
「瑾/瓊/璚/瑦/璀」长得像（都是王旁），但声符分别是堇/夐/盡/英/崔——
本来就不该一族。族里混着这种「同形不同音」的字，是方法的固有边界，
文档与演示页该说清楚（详见 	ools/diag_family_known.ts 里的对照组）。

#### E6 易混字对比：形似度该用骨架距离，不是像素 IoU

笔画配对修好了（汩/汨 从「共有 0 笔」变成 5 笔），但**形似度数值仍偏低**
（日/曰 26%、未/末 33%）。原因：字形是**细线条轮廓**，
像素 IoU 对亚像素偏移极敏感——两根几乎重合的线，错开半像素，交集就归零。

要真正量「像不像」，得用**骨架的 Hausdorff / 倒角距离**（对笔画中线算），
而不是对着填充区域算 IoU。这是下一步的事。

**但别急着换成形状描述子**——库里已有「与位置无关的形状描述子」
（12×12 归一化位图 + 长宽比桶），实测换过去是另一头翻车：

| 字对 | 像素 IoU（现状） | 描述子相似度 | 笔画配对 |
|---|---|---|---|
| 日/曰 | 26.1% | 59.1% | 1 |
| 未/末 | 32.5% | 80.1% | 1 |
| 土/士 | 37.5% | 93.0% | 1 |
| 汩/汨 | 41.4% | 81.8% | 5 |
| 木/本 | 39.2% | 88.7% | 1 |
| **人/大** | **2.7%** | **82.0%** | 0 |
| **未/目** | **7.2%** | **73.4%** | 0 |
| 日/水 | 6.9% | 41.1% | 0 |

描述子法**丢掉了位置**：笔画只要形状像就算配上，于是「人」和「大」
（结构完全不同的两个字）拿到 82%。像素 IoU 丢掉了**尺度鲁棒性**：
细线条轮廓错开半像素，交集就归零。

所以正确的指标应该是**两者的乘积**——形状用描述子（抗亚像素偏移），
位置用归一化的重心距离（保区分度），而不是任选其一。
这需要先想清楚「位置」该怎么量（笔画的相对位置？整体的骨架？），
不能拍脑袋，所以留到下一步。

### 2.5 隶变：默认参数不能太狠

用 RDP 简化把曲线折成折角，容差 6（在 400 单位的画布上）能把字形从
4000 点压到 60 点——简化率 98%，**字基本没了**。默认容差改成 3，
并把演示页的滑块上限从 30 降到 15。

### 2.6 隶变：规则要加在**中线**上，不是加在轮廓上

摹本的一笔是**闭合轮廓**（一圈描边），不是一条线。而隶变的四条规则说的都是
**笔势**：圆转方折说的是笔画中段的转折，波磔说的是收笔的走势——这些长在中线上。

直接对闭合环做折线简化，环会被压扁；在环上加尾巴，会凭空长出一个尖刺。
这正是隶变演示早先「一团乱」的成因。

修法：新增 `src/geometry/centerline.ts`，用**对边配对**求中线——
沿主轴找到轮廓的两个端点，走出「上边」「下边」两条弧，按弧长等比配对，
逐对取中点，两点距离的一半就是该处的笔宽。规则加在中线上，最后按原笔宽撑回轮廓。

配套的两条判据：

- **块状轮廓要判为退化**（返回 `null`，原样保留）。判据是「中线长至少要能解释这圈墨」
  （中线长 ≥ 0.75 × 半周长）：40×40 方块的中线长 56.7（沿对角线），比值 0.71 → 判为块状。
  不加这条，方块会被重建成一条斜穿过去的带子——比不改还糟。
- **闭合信息必须由解析层带下来**。SVG 的 `Z` 只是「首尾隐含相连」，解析出来的点列
  首尾**不重复**，所以「首尾重合」这个几何判据对真实字形一律失效。
  早先的 `isClosedSubpath` 因此在真实数据上**从来没成立过**，中线路径根本没被触发。
  现在 `parsePathDetailed` 把 `Z` 标记一路带到 `GlyphPath.closed`。

### 2.7 波磔幅度不能按字身缩放

早先的实现是 `waveAmplitude * 0.06 * 字身长边`。于是 `waveAmplitude: 10`
在 100 单位见方的字上变成 **105.6 单位**——比整个字还长。

现在 `waveAmplitude` 的语义是**绝对幅度**（用户单位，直接用，不缩放），
另加 `waveRatio`（占字身长边的比例，默认 0.025）作兜底。
隶书的波磔是收笔处一个小小的上扬，大约是字身的 2–3%，与字的大小无关。

### 2.8 笔画对应：必须一对一，必须先归一化

两处缺陷叠在一起，让「哪几笔在演变、哪一笔隐藏了、哪两笔浮出来」的结论**直接是错的**：

- **多对一**：`usedTo` 集合只写不读，同一条目标轮廓能被配两次。
  甲骨「日」→篆书「日」实得 `[[0,0],[1,0]]`——篆书那条轮廓配了两次。
- **没做画布归一化**：文档说「按墨迹外接框等比居中到同一张画布」，实现却各按自己的
  `viewBox` 光栅化。同样形状换个位置就配不上（`pairs 0 → 1` 修好后）。

修法：候选对按**分数降序全局贪心**占用，一个源笔画最多配一个目标笔画。
策略是量出来的，不是拍的——255 组真实字形对上，先到先得的配对数 618、Σoverlap 170.5；
全局贪心配对数 640、Σoverlap 220.1（高 29%）。

归一化**不能**复用 `normalizeToFrame`：它在**光栅像素空间**按 SVG 声明的 viewBox 量框，
而上游字形墨迹常跑到框外（实测「明」墨迹 x 到 −124）会被裁掉；
非正方形 viewBox（甲骨层 21×19）还会先被拉成正方形、形状变形。
新实现改在**字形坐标系**量墨迹。

> **遗留**：仓库现在有三套归一化口径（`normalizeGlyph` / `normalizeToFrame` /
> `correspond.ts` 内部那套），其中两套一致、`normalizeToFrame` 是异类。建议后续统一。

### 2.9 描述子距离：两个字符串不同，距离就必须大于 0

`descriptorDistance` 只比位图的**公共前缀**，`"1.00|0101"` 与
`"1.00|0101"` + 140 个 `0` 的距离算成 **0**。而这个量正被部首定位的投票阈值用着——
「距离 0」不再等于「同一形状」，不同的部首形会被判成同一个。

畸形描述子（缺 `|`）还会直接抛 `TypeError`。

现在：畸形一律返回 `Infinity`（不抛异常）；位图按**最长一侧对齐逐位比、缺位算不同**。
底线是「两个字符串不同 ⇒ 距离 > 0」。改前改后实测的准确率**完全相同**
（构形 62.0%、投票 48.9%、模板 43.5%），说明合法描述子的判定没被影响。

### 2.10 「异常情况」要钉成断言，不能靠人肉发现

这轮补测试时挖出 24 个缺陷（版式 13 个、对应与描述子 3 个、笔画与隶变 8 个），
其中 `advance(Infinity)` 会**死循环挂死**——用户输入透传上去就能把进程拖死。

这些缺陷不是「写测试时顺手发现的」，而是**测试必须覆盖的维度**：

1. 正常路径；2. 边界；3. **退化输入不抛异常**；4. 不变量 / 性质；5. 真实字形端到端。

第 3 层是验收标准：把每一条「异常情况」写成一条断言，钉死它应该抛还是应该返回什么。
早先发现的缺陷是用 `it.fails` 记下来的（缺陷还在时绿，修好后变红提醒改断言）——
这个约定比「先写断言、再修代码」省事，但**修完必须把 `it.fails` 转成正常断言**，
否则修好的代码会让测试变红。

### 2.11 三条**否定结论**：查了才知道不是那个问题

构形准确率停在 62.0%，想往上走就得知道卡在哪。于是写了探针
（`tools/diag_vote_gap.ts`、`tools/diag_descriptor.ts`）逐条量，量出来三件事，
**三条都推翻了原先的猜测**——记在这里，免得下次再走一遍。

**(一) 描述子没有退化。** 原以为「12×12 正方形归一化会把细笔画抹成全 1」，
实测 1,699 条笔画里位图全 1 的只有 **4 条（0.2%）**，平均墨占比 44.9%——
位图的信息量是够的。这条路不通。

**(二) 置信度阈值不是杠杆。** 投票法的「判不出」有 14 个卡在置信度
0.29–0.44，阈值 0.45 正好卡在分布中间，看着像是调一下就能多判一批。
扫了 0.15–0.60（`node tools/diag_vote_gap.ts --sweep`）：

| minScore | 投票法 正确/总数 | 投票法 精确率 | 组合模式 正确/总数 | 组合模式 精确率 |
|---|---|---|---|---|
| 0.30 | 50/92 = 54.3% | 73.5% | 57/92 = 62.0% | 66.3% |
| 0.35 | 50/92 = 54.3% | 75.8% | 57/92 = 62.0% | 67.1% |
| 0.40 | 47/92 = 51.1% | 78.3% | **58/92 = 63.0%** | 69.9% |
| **0.45**（现值） | 45/92 = 48.9% | **81.8%** | 57/92 = 62.0% | **70.4%** |
| 0.50 | 38/92 = 41.3% | 79.2% | 53/92 = 57.6% | 66.3% |

投票法单独看，降阈值能多对 5 个字；**但组合模式（投票优先、判不出回退模板）
只在 0.40 处高 1 个字（63.0% vs 62.0%），精确率反而下降**。
1 个字 / 92 个字在噪声里，而且要为它多担 1 个错判——不值得。**阈值保持 0.45。**

**(三) 真正的卡点是「码本没覆盖到这个部」。** 把 37 个「判不出」分成三类：

| 卡点 | 数量 | 说明 |
|---|---|---|
| **A** 这个部没归纳出偏旁形 | 13 | 码本只覆盖 124/540 部；部 408（心）一个就占 4 个字 |
| **B** 有偏旁形，但一笔都没命中容差 | 10 | 偏旁形与实际写法差太远，或容差太紧 |
| **C** 命中了，但置信度不足 | 14 | 见（二）——已经证明不是杠杆 |

所以要提准确率，**该动的是码本的归纳参数**（`--min-chars` / `--coverage` / `--cluster`），
不是运行时的阈值。

> **教训**：阈值、容差这类数字看着像「调一调就好」，但**先量分布再动手**。
> 上表里投票法和组合模式的最优点**根本不在一处**——只看单一方法的扫描结果
> 就会改错地方。

### 2.12 IDS 结构符说的是**版面**，不是构件顺序

左右结构一直发两个码：部首在左发 `⿰`，在右发 `⿲`。这是错的。

`⿲` 在 IDS 里表示「**第一构件写在右边**」——那是**构件顺序**的信息。
而本算法只知道「部首 + 其余」两方，**根本不知道 IDS 里哪一方写在前**。
「期」= 其 + 月，部首月在右，但它是**左右结构**，IDS 写作 `⿰其月`——
发 `⿲` 是不对的。

上下轴早先就已经修过同一件事（`⿱` 不再区分 `⿷`/`⿸`，方位归 `radicalSide`），
左右轴这处**漏了**。统一之后：并排就是 `⿰`，部首在哪一侧由 `radicalSide` 说。

> 效果：组合模式的构形准确率 **60.9% → 66.3%**（92 个可分解字，正确 56 → 61）。
> 混淆表里 `⿰→⿲ 5` 这一栏整个消失。

**教训**：同一个语义修正要**在所有分支上做一遍**。上下轴修了、左右轴没修，
是因为两处代码长得像但不在同一个函数里。

### 2.13 偏旁形码本的粒度：部首在字里的「粒度」不统一

部首偏旁形码本（`tools/build_radical_forms.ts`）是「同一个说文部下的所有字，
**共有**的那几笔」——覆盖过半的描述子就是部首笔画。

问题在于**部首在字里的粒度不统一**：

- 「語」的「言」**横跨路径 0 与路径 3**（顶上那一横单独一条路径）；
- 别的字里「言」是一条路径里的**若干子路径**。

码本只收**路径级**描述子时，「言」顶上那一横就永远匹配不上——
它在语料里很少单独成路径，覆盖度上不去，被 50% 的阈值切掉了。
于是部 56（言）在码本里只有 1 个型，「語」的部首定位只命中路径 0，漏了路径 3。

试过三条路：

| 方案 | 部覆盖 | 构形准确率 | 构建耗时 |
|---|---|---|---|
| 只收路径级（原方案） | 124 部 | 66.3% | 106 秒 |
| 路径级 + 子路径级都收 | 152 部 | **62.0%** | **约 30 分钟** |
| 路径级 + **部首自身的笔画** | **187 部** | **66.3%**（精确率 70.4% → **75.3%**） | 约 2 分钟 |

子路径级那条路两头都输：候选描述子翻几倍，而覆盖判据是 O(候选 × 字 × 笔画)，
**构建从 106 秒涨到约 30 分钟**；而且多收的型里混进假型，准确率还掉 4 个字。

**最终方案**：路径级不变，额外把**部首自身字形**的笔画收进码本。
理由是「部首自己长什么样」是**硬事实**——说文部的独立字形里就画着那一横。
放在覆盖度挑选**之后**追加：语料里的「共有写法」优先，独立形态只作补充
（「水」独立是中间一竖两边四点，作偏旁是三条波浪线，独立形态在这里恰恰是不可靠的那个）。

结果：部覆盖 124 → **187 部**，准确率**不变**，精确率还从 70.4% 升到 75.3%。

> **教训**：归纳「共有特征」时，**特征在哪一层**是个要先想清楚的问题。
> 上游数据的粒度不统一时，「共有」在不同层上的答案完全不同——
> 但选层之前先量一下**代价**（这里量的是构建耗时与准确率），
> 别被「看起来更全」的方案骗了。

### 2.14 形状距离里的长宽比要按**比值**算，不能按绝对差

形状描述子 = 12×12 位图（按自身外接框归一化）+ 长宽比桶。
距离 = 位图不同的位数 + 长宽比差 × 权重。

长宽比是**比值**，跨度极大（横笔 40、竖笔 0.03）。早先的 `|a1-a2| × 24`
（绝对差）于是出了两处毛病：

- 「語」路径 3 的长宽比 **7.33**，与部首「言」独立形态那一横的 **13.33** 差 6.0
  → **144 分**——与「位图完全不是一回事」等价，
  而这两个笔画的**位图只差 9 位**。一根横画与另一根横画，
  因为长短比例差一倍就被判成毫不相干。
- 更要命的是「7.33 与 13.33 差 6」听着不多，但绝对差乘 24 之后，
  它的分量已经和**整个位图**（144 位）一样重了。

改成 `|log(a1) - log(a2)| × 12`：比值差 2 倍记 8.3 分，
差 1000 倍（横 vs 竖）记 86 分——**尺度无关，量纲与位图的「差几位」也对得上**。

效果：「語」的部首定位从只命中路径 0 变成命中路径 **0 与 3**（与人工核验的期望一致）；
投票法单独跑从 45/92 提到 **47–48/92**（容差跟着放大到 38）。

> **教训**：给距离里的各个分量定权重时，要先问「这个分量的**量纲**是什么」。
> 位图的单位是「差几位」（0–144），长宽比的单位是「差多少」——
> 两者直接相加，乘什么权重都是拍脑袋。**比值型的东西要按比值算**（取对数差）。

### 2.15 演变插值要保留**全部**子路径

C1 的承诺是「t=0 完全等于源字形，t=1 完全等于目标字形」。早先的实现**没做到**：
每条笔画只取**最长**的那条子路径去插值。

摹本的一笔常常含多个子路径——外面一圈轮廓 + 里面几个反向绕向的洞
（小篆「日」就是外轮廓加两个洞）。只取最长的一条，**洞就没了**：
实测篆书「明」在 t=0 的墨量是 11088，而归一化后的源字形只有 7447——多出来的正是被填上的洞。

改成**逐条子路径插值**（按子路径下标配对，多出来的随 t 长/消），
t=0 就真的等于源字形了。代价是路径与子路径的对应关系从「一对多」变成「按下标配对」——
对齐不好的字（比如源有洞、目标没洞）中间态会略有偏差，但**端点是对的**，
而端点对得上是承诺里更重要的一半。

> **教训**：写「t=0 等于源」这种承诺时，要有一条**端点等价**的测试钉住它。
> 这次是靠子代理写不变量测试时才发现端点不等——单看中间态完全看不出问题。

### 2.16 构形判定的**兜底**是「包围」，而「宀」类盖头该是「上下」

准确率 65.2% 之后，最大的错误桶是「上下被判成包围」（⿱→⿴ 7 个字）。
把判定用的几何量摊开看（`tools/diag_structure_fails.ts`），字分三堆：

| 现象 | 字 | 几何 |
|---|---|---|
| **「宀」类盖头** | 宇 宙 家 室 安 富（6 个） | 部首框几乎等于整字框，其余被罩在里头，质心差 dx≈0、dy≈0.01–0.13 → 上下判据不成立 → 兜底成 ⿴ |
| **差一点点** | 常 | dy=0.16，SEP 阈值 0.18，**差 0.02** |
| **真·左右被误判** | 栠 棼 棽 | dx≈0（部首窄、其余宽，质心撞在一起）→ 落到上下判据 |

「宀」这一堆的根因很清楚：**篆书的宀是又高又对称的拱形**，几何上把下面的字整个罩住，
和「囗」围住没有区别。现有代码用 `isClosedFrame`（部首自身字形有没有封闭的空腔）
把「囗」（闭 → ⿴）与「门/匚/厂」（开 → ⿵）分开，**但分不出「对称的盖头」（宀 → ⿱）
与「单边的框」（厂/匚 → ⿵）**。

下一轮该做的事（**没做，留作线索**）：

1. 给「开口的部首」再分一类：**对称的盖头**（宀/冂/冖）与**单边的框**（厂/匚/广/门）。
   判据可以用部首自身字形的**左右对称性**（光栅化后与镜像求 IoU），
   再结合「其余件在部首框里的纵向偏移」。
2. 「常」这种差 0.02 的，说明 SEP=0.18 这个阈值在质心判据上偏硬——
   可以考虑改成**按部件的墨量分布**分位数（而不是质心）来定「上/下」的界。

> **教训**：兜底分支不是「实在分不出来时的默认值」，它**自己就是一个结论**。
> 这里的兜底是 ⿴（全包围），于是所有「分不出左右也分不出上下」的字都被断言成包围。
> 兜底选哪个结构符，等于给一大片模糊地带下了定论。

## 三、工程上的坑

### 3.1 演示页用经典脚本，不用 ES module

最初演示页是 `<script type="module">` + `import`。在某些浏览器环境里
**模块脚本的加载会卡住**——请求发出去了，服务器也正确响应了（原始 TCP 探针
4 ms 收齐 1220 字节，响应头完全正确），但浏览器那边的模块图**永远不完成求值**。
同样的 URL 用 `fetch()` 取完全正常。

改成：esbuild 打成单文件 IIFE（`window.HanziAlgorithms`）+ 经典脚本引用。
零构建、任何静态服务器都能跑，还顺手去掉了模块解析这一层不确定性。

**教训**：演示页的第一要务是「打开就能用」，不要引入模块图这种隐式依赖。

### 3.2 用 127.0.0.1，不要用 localhost

浏览器把 `localhost` 先解析到 `::1`。服务器只监听 IPv4 时，每次请求都要等
一次 IPv6 连接超时才回退到 IPv4——**每次请求多等 5 秒**，页面看起来像卡死。

修法两个都做：服务器双栈监听（`server.listen(port, "::")`），文档与演示页
一律用 `127.0.0.1`。

### 3.3 索引表不能整个进浏览器

六层书体的索引表加起来 **22 MB**。让浏览器拉全再自己筛，页面直接卡死。

两条路都试过：
- 服务器端筛选接口（`/api/rows?layer=seal&char=日`）——能用，但演示页就绑死在
  这个自定义服务器上，换个静态服务器就跑不起来；
- **预生成静态索引**（`assets/index/<层>.json`，30–290 KB）——演示页只 fetch
  静态文件，任何静态服务器都能跑。

最后选了后者。

### 3.4 数据量要能分段跑

全量 10,591 个字跑一遍数据生成要近两小时，超过了单次后台任务的上限。
所以生成器带 `--start` / `--limit`，可以分段跑。

### 3.5 `setPointerCapture` 会抛错

描红演示里 `svg.setPointerCapture(ev.pointerId)` 对**合成事件**（自动化测试、
某些辅助设备）会抛 `InvalidStateError`，一抛就把整段处理打断——用户看到的是
「按了没反应」。加了 try/catch，抛了就当没捕获，不影响描红本身。

### 3.6 canvas 覆盖层会把底本盖住

描红演示原本用 `<canvas>` 叠在 SVG 上。canvas 铺满整个格子，尺寸算错时
会把描红底本完全遮住（看起来像「字没画出来」）。改成纯 SVG——学生笔迹也
画成 `<path>`——顺带去掉了 canvas 的尺寸与 devicePixelRatio 麻烦。

### 3.7 并发请求多了会「发出去了但永不落地」——以及一个更根本的浏览器限制

现象：**请求确实到了服务器（服务器日志有记录，响应也发得出去），但浏览器
端的 promise 永远不 settle**，页面看着像卡死。

排查过程：

- 同一页面先并发取 8 个索引、再并发取 5 个字形 → 后一批卡住；
- 改成**串行**取 → 立刻通；
- 换 Python 标准服务器（`http.server`）→ 一样卡 —— **所以不是服务器的问题**；
- 用 Node 的 `fetch` 并发拉同样的 URL → 67 ms 全部完成 —— **也不是网络的问题**。

最后用一个**只做串行 fetch 的最小页面**（12 个 URL）复测：
第 1、2 个请求正常（16 ms / 12 ms），**第 3 个开始永远不落地**。

也就是说：**是这个浏览器会话的网络栈本身坏了**（当时已开了 30 多个标签页、
发了四百多个请求），不是仓库代码的问题。同一份代码换个干净的浏览器就正常。

据此做了两件事（都保留，因为它们在任何受限环境里都有用）：

1. 演示层加**并发限制器**（`demos/lib/demo.js` 的 `withLimit`），同时在飞的
   请求压到 2 个，其余排队。代价可以忽略。
2. 演变链改为**串行**取（`demos/03-evolution.html`、`demos/06-lab.html`）。

**教训一**：演示页要能在「浏览器 + 任意静态服务器 + 任意网络环境」里跑通，
就不能假设并发请求一定拿得到响应。

**教训二**：**验证要分清「代码错了」和「环境坏了」**。这次的弯路在于：一直在
改自己的代码，而真正该改的是验证方法——先用**最小复现页面**把环境问题隔离出来，
再去改代码。否则会为了迁就一个坏掉的浏览器，把代码改坏。

**教训三**：浏览器里的行为要能在 Node 里复现才算数。本仓库的演示页数据流
（取索引 → 取字形 → 跑算法 → 出 SVG 数据）都写进了 `tests/demos.e2e.test.ts`，
演示页出问题时先看这个测试。

### 3.8 服务器的响应方式也有讲究

本地服务器踩了两遍：

- **走 chunked 编码时**，有些浏览器收不到结束标记 → 同样表现为 promise 不 settle。
  改成给明确的 `content-length`。
- **每个请求都关连接**时，浏览器会不断新建 TCP 连接，短连接的 TIME_WAIT 会
  累积；本机 TIME_WAIT 涨到几十个后新连接就建不起来了。改成保持连接
  （`server.keepAliveTimeout = 60000`），让浏览器复用。
- 中间还自己踩了一次：`res.end(data)` 之后立刻 `res.destroy()` —— 那会在数据
  刷出去之前把连接掐断，浏览器收到截断的响应，promise 同样不会 settle。

### 3.9 字形仓的缓存不能无上限

全量跑数据生成时，字形仓把读过的每个字形都缓存住 —— 两千个字就把内存吃到
**2.9 GB**，机器被挤得连浏览器渲染进程都卡住（表现又是「fetch 不落地」）。

改成 LRU 式淘汰（`tools/lib/store.ts`，上限 256 个）。

**教训**：批处理工具的内存占用要和批处理规模无关。

## 四、约定

### 4.1 相对导入统一用 `.ts` 扩展名

Node 原生跑 TypeScript（Node 22.18+ / 24）要求相对导入写 `.ts`
（`./foo.ts`），而 tsc 靠 `rewriteRelativeImportExtensions` 在产物里改写成 `.js`。
新增文件时用 `.ts`，跑 `node tools/rewrite-imports.ts src tests tools` 批量校正。

### 4.2 算法必须可测，置信度必须诚实

- 每个算法至少有单测；能在真实字形上验证的，还要有端到端断言；
- 输出带置信度，说不准的时候**返回空**，不许硬给答案。
  部首定位置信度不足返回 `null` 是有意为之，不是 bug。

### 4.3 生成物必须标为生成物

形变插值出来的中间形态、隶变的结果，都**不是任何历史书体的摹本**，
文档与演示页都要写明这一点。

### 4.4 演示页的数据流要能在 Node 里验

演示页做的无非四步：取索引 → 取字形 → 跑算法 → 生成 SVG 数据。
这四步都写进 `tests/demos.e2e.test.ts`——**演示页出问题时，先看这个测试，
再看浏览器**。浏览器那层会受环境影响（见 3.7），测试不会。
