## 三、发布前要处理的事（本次只处理了第 3 条，其余留到下一版）

### 1. CI 现在会红：`verify.yml` 用 Node 20，工具脚本却要求 Node ≥22.18（**已复现**）

`verify.yml` 里 `setup-node` 写 `node-version: "20"`，但工作流最后一步要跑
`node tools/build_bundle.ts`——`tools/**` 是按「Node 原生跑 TS」写的（相对导入带 `.ts` 扩展名，
见 `AGENTS.md` 的 `rewrite-imports`）。Node 20 不认 `.ts` 扩展名：

```
> npx -y node@20 tools/build_bundle.ts
TypeError [ERR_UNKNOWN_FILE_EXTENSION]: Unknown file extension ".ts" for …\tools\build_bundle.ts
```

本机是 Node 24（22.18+ 默认剥类型），所以本地一直是对的，**推到 GitHub 第一次 CI 就会挂在这一步**。

修法（推荐）：`verify.yml` 的 `node-version` 改 `"24"`；`package.json` 的 `engines` 从 `>=20`
改 `>=22.18`；README 的「开箱即用」补一句 Node 版本要求。
（备选：CI 里改成 `npx tsx tools/build_bundle.ts`——要多一个依赖，不推荐。）

### 2. 还有四个文件带中文乱码（U+FFFD）——**本次未修**

原先五处，`THIRD_PARTY_NOTICES.md:35` 的那处已随本次许可修改一并改掉；**剩这四处**，全库只剩这些：

### 4. 仓库元数据与 README 的四个缺口（**本次没做，作者说下次**）

- `package.json` 缺 `repository` / `homepage` / `bugs`——GitHub 不会自动关联，npm 上也看不出来源；
- README 缺**在线预览**入口（Pages 地址）与 Node 版本要求；
- README 的「库怎么用」写 `import … from "hanzi-algorithms"`，但这个包**没有发布到 npm**，
  照抄会 import 不到——要么补一句「尚未发布 npm，可从源码构建或按 git 依赖装」，要么真发 npm（不建议现在做）；
- 仓库 About 需要手填（文案已备好），Topics 20 个也已备好，都在 [`docs/仓库描述.md`](仓库描述.md)。

### 5. `release` 分支过期了，别再拿它直接推

`release` 停在 `f37c725`（"汉字算法库：把字形变成结构的一组可复用算法"），
比 `main` 少了 `docs/仓库描述.md` 那一个提交。**要么删掉重建，要么改推 `main`**（见 §四·4 的方案 A/B）。

### 6.（可选但建议）根目录没有 `LICENSE`，GitHub 侧栏不会显示许可

本仓是三份许可（`LICENSE-CODE` MIT / `LICENSE-DOCS` CC0 / `LICENSE-DATA` 说明），
但 GitHub 的许可识别基本只认根目录的 `LICENSE`（或 `LICENSE.md` / `COPYING` 等少数几个名字），
现在侧栏是空的。
建议把 MIT 全文放成根 `LICENSE`（代码是本仓主体），`LICENSE-DOCS` / `LICENSE-DATA` 保持不动，
README 的许可表补一行说明「根 `LICENSE` 即代码许可」。
（兄弟仓反过来：根 `LICENSE` 放的是数据的 CC BY 4.0，侧栏就显示 CC BY——那是它的取舍。）

#### 方案 A：推完整历史（备选；作者已选下面的方案 B）

```powershell
git push -u origin main
```

三条理由（v1 定的是「压成一个提交」，这里记下另一面的取舍）：

1. **历史已经审计干净**：没有 `assets/`、没有 >1 MB 的对象、没有凭据，903 KiB 的 pack 本来就该保留；
2. **不会和本地分叉**：压成单提交后，远端 `main` 与本地 `main` 没有共同祖先，
   以后每次发布都得再走一次 orphan 分支或强推，是个长期的坑；
3. **提交信息本身就是可信度**：「修好路径解析器：构形准确率 23.3% → 62.0%」这类记录，
   比一个漂亮的首次提交更能说明这个库是怎么长出来的。

#### 方案 B：压成一个干净的首次提交（**作者已选**）

```powershell
git branch -D release              # 旧的 release 停 f37c725，已过期，先删
git checkout --orphan release
git add -A
git commit -m "汉字算法库 v0.1.0：把字形变成结构" `
           -m "- 结构：A1 部首定位、A2 构形分解、A2b 部件分块、A3 笔画切分" `
           -m "- 形变：C1 跨书体对应与插值、C2 隶变" `
           -m "- 排版：D1 竖排、D2 古籍版式、D3 行款推进" `
           -m "- 教学：E1 描红底本、E2 逐笔评分、E3 字表检索、E4 形声分析、E5 笔画统计" `
           -m "- 演示：单页 Tab 浏览页 + 七个算法页，字形子集入库，clone 下来即可看" `
           -m "- 实测：400 个用例全绿；构形 65.2%（92 个可分解字）；部首 11/11 手校命中"
git push -u origin release:main
git checkout main                  # 回到本地历史，main 一点不动
```

首次提交文案（与上面的命令同一份，留作核对）：

```

- 结构：A1 部首定位、A2 构形分解、A2b 部件分块、A3 笔画切分
```

### 阶段 8：打首个版本（10 分钟）

```powershell
git tag -a v0.1.0 -m "hanzi-algorithms v0.1.0：首个公开版本"
git push origin v0.1.0
```

> 走了方案 B 的话，tag 要打**远端那个提交**（`git tag -a v0.1.0 origin/main`，或 checkout 回
> `release` 再打）——打在本地 `main` 上会指向一串没推上去的历史，Release 页面就挂空了。

在 GitHub 上把它写成 Release，正文用四段：**是什么**（一句话）、**能看什么**（Pages 地址）、
**实测数字**（400 用例、构形 65.2%）、**边界**（不发布字形、中间形是算法生成的）。
兄弟仓没有任何 Release，这里做了就是净增益。

3. 若之后要补 v2 未做的收口（CI Node 版本、5 处乱码、元数据），走一个补丁提交 + 补丁版本即可。
