# hanzi-algorithms

**汉字结构计算库**——把「字形」变成「结构」的一组可复用算法。

输入是字形 SVG，输出是结构化的结果：部首在哪、笔画怎么切、构件怎么拆、字怎么演变、版面怎么排。

这个仓库发布**算法与代码**，以及**一小份演示用的字形**。
完整的字形库在兄弟仓库
[`hanzi-glyphs-svg`](https://github.com/zhouyongh/hanzi-glyphs-svg)（631 MB），
本仓只取每层十几个字做演示，出处与许可见 [`demos/data/PROVENANCE.md`](demos/data/PROVENANCE.md)。

**开箱即用**（演示用的字形子集已入库，需要 **Node ≥ 22.18**——工具脚本按 Node 原生跑 TS 写的）：

```bash
npm install
node tools/serve.ts            # 起本地服务器 → http://127.0.0.1:8080/
```

想跑**完整**字形库上的算法与测试（可选，素材只落在本地、不入库）：

```bash
node tools/sync_glyphs.ts      # 同步完整字形到本地 assets/（631 MB，不入库）
node tools/build_index.ts      # 生成演示用的静态索引
```

> **完整素材是本地素材**：`assets/` 整个目录在 `.gitignore` 里，仓库里只有演示子集。
> `demos/lib/hanzi-algorithms.js`（算法打包产物）也是**入库**的，所以演示页不需要先编译；
> 改算法后跑 `npm run build && node tools/build_bundle.ts` 重新生成即可。

> 用 `127.0.0.1` 而不是 `localhost`：浏览器把 `localhost` 先解析到 `::1`，
> 只监听 IPv4 时每次请求都要等一次连接超时回退，页面看起来像卡住。

## 五类算法

### A1 部首定位 —— 点一下小篆，选出它的部首

**难点**：字形是一个填充路径，部首在哪、哪几笔属于它，全靠人眼。

**关键洞察**：**部首字形本身就是仓里一张现成的小篆**（说文 540 部，每个部首字都有独立的篆书字形）。
于是问题从「识别未知的部首」变成「在复合字里定位一个已知形状」——标准的模板匹配。

**做法**：自研 SVG path 解析 → 光栅化 → **各向异性**尺度搜索（部首作偏旁时常被纵向拉长，
实测「手」作偏旁时横向压到 0.50、纵向保持 0.90）→ FFT 归一化互相关 → 路径归组。

**实测**（说文 540 部，11 个手校样例全部命中；批量 400 字 132 ms/字）：

| 字 | 说文部 | 命中笔画 | 互相关得分 | 部首笔画占全字墨量 |
|---|---|---|---|---|
| 投 | 441 手 | 0 | 0.78 | 43% |
| 指 | 441 手 | 0 | 0.83 | 45% |
| 持 | 441 手 | 1 | 0.83 | 42% |
| 想 | 408 心 | 0 | 0.52 | 40% |
| 好 | 443 女 | 0 | 0.57 | 55% |
| 如 | 443 女 | 0 | 0.56 | 65% |
| 河 | 410 水 | 0, 3, 4, 5 | 0.49 | 59% |
| 眼 | 99 目 | 1 | 0.55 | 37% |
| 語 | 56 言 | 0, 3 | 0.48 | 52% |
| 明 | 239 朙 | 0, 1, 2 | 1.00 | 100% |
| 本 | 206 木 | 0 | 0.81 | 100% |

置信度不足时返回 `null` 而不是硬给答案——部首说不准时，宁可不给。

> **光栅化按「墨迹范围」取景，不按 SVG 声明的 viewBox。**
> 上游篆书字形声明 `viewBox="0 0 400 400"`，但路径坐标会跑到框外
> （实测「明」的墨迹 x 到 −124、y 到 −171）。按声明框裁会丢掉三分之一的字，
> 而偏旁笔画多在字的边缘，裁掉的恰好是部首笔画。
> `RadicalOptions.frame` 可以切回声明框，默认是 `ink`。
>
> **光栅化之外还有一条：拿「偏旁形」比，别拿「独立形态」比。**
> 小篆的「眼」= ⿰目艮，而「艮」里本来就含一个「目」形的框——两者形状上分不开。
> 说文部首的**独立形态**（⿵ 那样一个大方框）跟它在合体字里的**偏旁形态**
> （窄窄的一个框）不是一回事，拿独立形态当模板必然挑错。
> 库里默认走「投票优先、判不出回退模板」的组合模式（见 A2 一节）。

> ⚠️ **构形分类（A2）目前只有 65% 准确率**（92 个带人工标注 IDS 的可分解常用字）。
> 这个数字一路改过四回：**37%（报的）→ 23.3%（分母修正后）→ 62.0%（解析器修正后）→ 65.2%（IDS 语义修正后）**。
>
> 早先那个 37% 有两处问题：
> 1. **分母是错的**——评测脚本把 24 个在篆书层里查不到的标注字静默跳过了，剩下 46 个；
> 2. **46 个里有 17 个是平凡正确的**——說文 540 部里 60 来个部本身就是合体字
>    （林、里、男、宮、明…），部首就是整字，算法只能给 ⿻。
>    等于那 37% 里有 37 个百分点是白送的。
>
> 现在分母是 92 个**可分解**的字（说文部首 ≠ 整字），平凡正确的独体字单列报，
> 脚本还会明确报出跳过了几个、为什么。
>
> 三条路径的实测对比（92 个可分解字，`node tools/eval_structure.ts --method=both`）：
>
> | 路径 | 做法 | 正确 | 判错 | 判不出 |
> |---|---|---|---|---|
> | 模板法 | 拿部首的**独立形态**做模板匹配 | 54.3% | 25.0% | 20.7% |
> | 投票法 | 拿归纳出的**偏旁形**按笔画形状投票 | 51.1% | 14.1% | 34.8% |
> | **组合**（默认） | **投票优先，判不出回退模板** | **65.2%** | 23.9% | 10.9% |
>
> 两条路径互补而非替代：投票法准但只在归纳出偏旁形的部上可用（覆盖 188/540 部），
> 模板法哪都能用但常落错处。库里因此提供 `structure/resolve.ts` 的 `resolveStructure()`。
> 典型例子是「眼」：小篆的「艮」里本来就含一个「目」形的框，形状上分不开——
> 模板法找到「艮」，偏旁形投票法才找得到「目」。
>
> ⚠️ **偏旁形码本（`assets/index/radical-forms.json`）是派生素材，改了形状距离就要重建**：
> `node tools/build_radical_forms.ts`（约 2 分钟）。码本与运行时口径不一致时，
> 评测数字量的是「半新半旧」，会偏低 1 个字左右。
>
> 另外三处修正：部件按**子路径**划分（篆书层里一条 `<path>` 常含多个子路径，
> 而它们不一定属于同一部件）；相对位置用**墨量质心**判（框会因部件交叠而失效）；
> 全包围（⿴）与左上包围（⿵）靠部首独立字形有没有**封闭空腔**区分。
>
> 最大的一个坑其实是**路径解析器**：小篆「日」在 SVG 里是一条路径三个子路径
> （外轮廓 + 两个反向绕向的洞），而解析器把 `z` 之后相对 `m` 的偏移丢了，
> 洞没了、字形歪了——六个书体里 **58%–79%** 的字形都踩这个模式。
> 详见 [`docs/设计取舍与踩坑.md`](docs/设计取舍与踩坑.md)；仓库里有准确率下限测试守着这条线。
### A2 构形分解 —— 从几何关系推出 IDS 结构符

不查表。从部首定位结果推出左右（⿰）、上下（⿱）、包围（⿵）等结构。

- 部件的最小单位是**子路径**（不是 `<path>`）；
- 相对位置用**墨量质心**判断，不用外接框（篆书部件常交叠，框会横跨整个字）；
- 结构符说的是**版面**；部首在哪一侧由 `radicalSide` 单独给出
  （「想」= ⿱相心，版面是上下，但说文部首「心」在下）；
- 高层入口 `resolveStructure(glyph, radicalGlyph, { radicalTypes })`：
  投票优先、判不出回退模板，返回用了哪条路径。

好处是能覆盖现有 IDS 集覆盖不到的摹本字形；代价是「包围但偏心」这类字形会退化成通用的 ⿴。

### A2b 部件分块 —— 把一个字切成「左 / 右上 / 右下」

构形分解只回答「部首在哪」，教学上真正要指认的是**块**：「投」是扌 + 几 + 又三块，
点右上那块就该**整块**亮起来，而不是亮其中一笔。

做法是纯几何的**递归二分**：按「到最近轴线的分离度最大的轴」切一刀，
再对切出来的每一块继续切；标签按切分方式叠加（「左」组再上下切 → 左上 / 左下）。
阈值与 A2 的几何判据一致（18% / 55%），两处对同一个字给出的结构不会互相打架。

实测篆书「投」切成 `左[扌] 右上[几] 右下[又]`，「想」切成 `上左 / 上右 / 下`——
和人的直觉一致。

### A3 笔画切分与笔顺

- **甲骨骨架**：一 stroke 一 `<path>`，**文件里的出现顺序就是落笔顺序**（1,203 条抽查全等）——
  所以笔顺不用另存一份数据。
- **摹本轮廓**（篆/金/隶）：一 `<path>` 一摹本笔画。

两种形态统一成同一套 `Stroke` 结构，动画层据此决定是「按折线书写」还是「整笔显现」。

### C1 字形演变 —— 一个字连续变成另一个字

1. 两个书体的字形各自按墨迹外接框等比居中到同一坐标系；
2. 源字形每条笔画在目标字形里找重叠最大的那笔（甲骨 ∩ 篆 = 852 字，92.3% 可建立部分对应）；
3. 配对的轮廓按**弧长等距**重采样到同样点数；
4. 逐点线性插值，中间每一帧都是合法路径。

> 中间形态是**算法生成的过渡形**，不是任何历史书体的摹本。演示页与 API 文档都写明了这一点。

### C2 隶变算法 —— 把篆书按隶书规则做几何变换

| 隶书规则 | 几何实现 |
|---|---|
| 圆转方折 | 折线简化（RDP）+ 近水平/垂直段吸附到轴向 |
| 线条波磔 | 横向收笔处加波峰 |
| 横平竖直 | 笔画主方向旋到最近的轴 |
| 象形性降低 | 曲线压缩 + 容差简化 |

> 输出是「算法生成的隶变示意」，**不是隶书摹本**。真实隶书字形需另行取得授权后单独入库。

### D1 / D2 / D3 排版

- **D1 竖排**：列从右往左、列内自上而下；**句读点号移到字格右上角**（横排时在左下角，
  这是汉字排印里最容易被忽略的一条规则）；成对括号引号转向。
- **D2 古籍版式**：参数化生成半叶——版框、界行（双线）、版心、双鱼尾、天地头脚。
- **D3 行款推进**：逐字推进的游标，供「按笔顺逐字书写」的应用调用。

### E1 / E2 / E3 / E4 / E5 教学辅助

- **E1 描红底本**：把字形压成浅色轮廓。输出是**渲染无关的描述**（描边型给折线与笔宽，
  填充型给闭合轮廓），下游用 SVG / Canvas / PDF 都能画。
- **E2 描红评分**：学生写的与范字**逐笔比对**——覆盖率（范字这一笔被你盖住多少）
  与精确率（你写的这一笔落在范字里多少）的调和平均，再加整体形似度。
  能指出「第 3 笔最不像」和「你多写了 2 笔」；**笔顺写反也扣分**
  （逐笔得分按形状算，形状对但顺序错同样要罚）。
- **E3 字表检索**：按部首、笔画数、结构符、书体组合过滤字表；另有部首分组与频次统计。
- **E4 形声分析**：从构形分解推出哪边是形符、哪边是声符，带**置信度**；
  格局与常规相反时（如右左结构）会明说「存疑」。
- **E5 笔画统计与笔顺检查**：笔画数、总长、方向直方图；笔顺连贯性检查
  （骨架字形的文件顺序就是落笔顺序，所以不会误报「笔序有误」）。

- URL 带 `#radical` 这样的锚点，可以直接链到某个算法；
- `←` `→` 在 Tab 之间跳；
- 每个算法页也是独立页面，可以单独打开（面板右上角有「↗ 单独打开」）。

实现上，单页浏览页用 **iframe 内嵌**各算法页（首次切到该 Tab 才加载），
而不是把七页合并成一个文档：合并要动一百多个 id，回归风险高；
iframe 里每个算法拿到完整的一页（自己的标题、说明、工具条），
挨个看效果时上下文完整。内嵌时演示页会藏掉自己的那排导航（`?embed=1`）。

零构建：浏览器直接跑编译产物 `demos/lib/hanzi-algorithms.js`。

## 库怎么用

```ts
import { parseGlyphSvg, locateRadical, decompose } from "hanzi-algorithms";

const glyph = parseGlyphSvg(await readFile("投.svg", "utf8"));
const radical = parseGlyphSvg(await readFile("3F30C.svg", "utf8")); // 「手」

const match = locateRadical(glyph, radical);
if (match) {
  console.log(match.pathIndices);   // [0] —— 第 0 笔属于手部
  console.log(match.score);         // 0.617 归一化互相关
  console.log(decompose(glyph, match).structure); // ⿰ 左右结构
}
```

运行时**零依赖**，只用到 TypeScript 标准库。构建产物是 ESM + `.d.ts`。

## 边界

- **不发布字形。** 本地同步，仓库里只有算法与代码。
- **不做字典。** 字与字之间的释义、异体、版本对照归 `hanzi-relations`。
- **不做通用字体引擎。** 排版只覆盖「汉字竖排 + 古籍版式」这一类。
- **不确定就说不确定。** 每个算法都带置信度，低置信度时返回空。

## 为什么这么做

实现过程中的取舍与踩过的坑记在 [`docs/设计取舍与踩坑.md`](docs/设计取舍与踩坑.md)；
**这个仓库怎么搭的**（语言、分层、依赖策略、动画底子、测试策略）记在
[`docs/架构.md`](docs/架构.md)。几条最要紧的：

- **部首定位为什么能做出来**：部首字形本身就是仓里一张现成的小篆，于是问题从
  「识别未知的部首」变成「在复合字里定位一个已知形状」。
- **为什么必须用归一化互相关**：小模板落在实心笔画里，重叠量也是满分。
- **为什么尺度要横纵分开搜**：部首作偏旁时常被纵向拉长（实测「手」作偏旁时
  横向压到 0.50、纵向保持 0.90）。
- **为什么光栅化按墨迹范围取景**：上游字形的路径会跑到声明的 viewBox 外面，
  按声明框裁掉的恰好是长在字边缘的偏旁笔画。
- **为什么路径解析器不能漏掉 `z` 之后的相对 `m`**：小篆「日」是一条路径三个子路径
  （外轮廓 + 两个反向绕向的洞），漏掉相对偏移就等于把洞填了、把字画歪——
  六个书体里 58%–79% 的字形都踩这个模式。**视觉输出不对劲时先怀疑数据通路。**
- **为什么隶变要先求中线**：摹本的一笔是**闭合轮廓**，规则直接加在轮廓上会把它压扁、
  在环上凭空长出尖刺。规则要作用在**笔势线**上，再按原笔宽撑回轮廓。
- **为什么波磔幅度不能按字身缩放**：早先的 `waveAmplitude * 0.06 * 字身长边`
  会让尾巴比整个字还长——隶变演示「一团乱」的根因。
- **为什么笔画对应必须做画布归一化**：不归一化的话，同样形状换个位置就配不上；
  归一化必须在**字形坐标系**量墨迹（按声明 viewBox 量会把跑到框外的字裁掉）。
- **为什么配对必须一对一**：多对一时同一条目标轮廓会被配两次，
  「哪几笔在演变、哪笔隐没、哪笔浮出」的结论直接是错的。
- **为什么演示页用经典脚本不用 ES module**：模块图会把演示页绑死在浏览器的
  模块加载器上，实测某些环境下模块脚本的加载会卡住。
- **为什么单页浏览页用 iframe 内嵌各算法页**：合并成一份文档要动一百多个 id，
  回归风险高；iframe 里每个算法拿到完整的一页，挨个看效果时上下文完整。
- **为什么强调用 `127.0.0.1`**：浏览器把 `localhost` 先解析到 `::1`，
  只监听 IPv4 时每次请求都要等一次连接超时回退。
